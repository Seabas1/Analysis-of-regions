# Обзор скриптов: что делает каждый и как он устроен

Разбор всех 11 скриптов проекта: назначение, входы и выходы, ключевые места кода и приёмы,
которыми решены технические проблемы. В конце — что автоматизировано полностью, что введено
руками, и какие расхождения нашлись при проверке кода.

---

## 1. Общая картина

Пайплайн линейный: **сбор → парсинг → анализ**, плюс отдельно сборка презентации.

```
                    ЭТАП 1. СБОР
rosstat.gov.ru ─────▶ download_rosstat.py ────────▶ data/rosstat/*.rar, *.pdf
Nominatim      ─────▶ get_region_boundary.py ─────▶ data/osm/region_boundary.geojson
Geofabrik      ─────▶ download_osm_pbf.py ────────▶ data/osm/*.osm.pbf (775 МБ)
trudvsem API   ─────▶ parse_vacancies_trudvsem.py ▶ data/labor/vacancies.csv (4 183)

                    ЭТАП 2. ПАРСИНГ
*.rar (22 docx) ────▶ rosstat_docx_to_text.py ────▶ data/rosstat/.../txt/R_*.txt (823 таблицы)
txt-дампы      ─────▶ rosstat_extract_region.py ──▶ saratov_tables.json/txt (397 таблиц)
PBF + полигон  ─────▶ parse_osm_objects.py ───────▶ data/osm/objects.csv (2 432)
objects.csv    ─────▶ assign_cities.py ───────────▶ data/osm/objects_by_city.csv

                    ЭТАП 3. АНАЛИЗ
все три таблицы ────▶ aggregate.py ───────────────▶ analiz/*.csv (3 файла)

                    ОФОРМЛЕНИЕ (вне пайплайна)
analiz/ + шаблон ───▶ make_presentation.py ───────▶ презентация .pptx (19 слайдов)
```

Все скрипты используют одну схему путей:

```python
PROJECT = os.path.dirname(os.path.dirname(os.path.abspath(__file__)))
```

То есть корень проекта вычисляется от расположения самого файла скрипта: `scripts/какой-то.py` →
на уровень выше. Поэтому проект работает из любой папки, а не только с диска автора.

Формат обмена — файлы. Ни один скрипт не вызывает другой и не знает о его существовании: он читает
файл и пишет файл. Отсюда два свойства: любой этап перезапускается отдельно, а порядок запуска
задан не кодом, а зависимостями по данным.

## 2. Сквозные приёмы

### 2.1 Идемпотентность: «уже скачано — пропускаем»

Дорогие операции не повторяются. В загрузчиках проверяется существование файла и его размер:

```python
if os.path.exists(dest) and os.path.getsize(dest) > 100000:
    print("[skip] %s уже есть" % name)
    continue
```

Порог по размеру нужен, чтобы не принять за готовый файл обрывок: если скачивание прервалось,
файл существует, но он меньше ожидаемого, и скрипт скачает его заново. Тот же приём в
`download_osm_pbf.py`, но с порогом 0,7 ГБ.

### 2.2 Кэш ответов геокодера

`assign_cities.py` обращается к Nominatim за координатами 27 городов. Nominatim ограничивает
частоту запросов, поэтому ответы кэшируются в файл, а между запросами стоит пауза:

```python
cache = os.path.join(OSMDIR, "cities_geo.json")
if os.path.exists(cache):
    geo = json.load(open(cache, encoding="utf-8"))
else:
    for name in CITIES:
        ...
        time.sleep(1.1)          # вежливость к бесплатному сервису
    json.dump(geo, open(cache, "w", encoding="utf-8"), ensure_ascii=False, indent=1)
```

Побочный эффект приятный: повторный запуск привязки идёт секунды и не зависит от доступности
внешнего сервиса. Этот приём уже спасал проект, когда Nominatim начал отвечать ошибками.

### 2.3 Повторы с растущей паузой

Сетевые сбои в `parse_vacancies_trudvsem.py` обрабатываются тремя попытками с увеличивающейся
задержкой:

```python
for i in range(3):
    try:
        ...urlopen(req, timeout=45)...
        return json.loads(...)
    except Exception:
        time.sleep(1.5 * (i + 1))   # 1,5 с → 3 с → 4,5 с
return None                         # сдались — вызывающий код просто пропустит ключ
```

Важно, что окончательная неудача не роняет весь сбор: возвращается `None`, и обработка
продолжается. При 129 ключевых словах потеря одного-двух не критична.

### 2.4 Параллелизм и дедупликация

129 ключевых слов собираются в 5 потоков — сеть ждёт, а не процессор, поэтому потоки дают
почти пятикратное ускорение:

```python
with ThreadPoolExecutor(max_workers=5) as ex:
    futs = {ex.submit(collect_kw, kw): kw for kw in KEYWORDS}
    for f in as_completed(futs):
        kw, got = f.result()
```

Дедупликация сделана не отдельным проходом, а структурой данных: каждый поток возвращает
**словарь** `{id_вакансии: вакансия}`, а результаты сливаются в общий словарь `seen`. Поскольку
`id` уникален, повторные вхождения из разных поисковых запросов просто перезаписывают друг друга:

```python
for k, v in got.items():
    if k not in seen:
        seen[k] = v
```

### 2.5 Векторная геометрия вместо циклов

Проверка «точка внутри полигона» — самая тяжёлая часть проекта: 47 658 объектов против контура
из 8 307 точек. Если проверять каждый объект циклом по точкам контура, это 400 млн сравнений
на чистом Python. Вместо этого — лучевой метод, векторизованный через numpy:

```python
def ray_inside(poly, pts):
    x, y = pts[:, 0:1], pts[:, 1:2]           # (N, 1)
    x1, y1 = poly[None, :, 0], poly[None, :, 1]   # (1, M)
    x2 = np.roll(poly[:, 0], -1)[None, :]     # соседняя вершина ребра
    y2 = np.roll(poly[:, 1], -1)[None, :]
    cond = (y1 > y) != (y2 > y)               # ребро пересекает горизонталь точки
    xint = (x2 - x1) * (y - y1) / (y2 - y1) + x1
    return (cond & (x < xint)).sum(axis=1) % 2 == 1   # нечётное число пересечений = внутри
```

Что здесь происходит: точка считается внутри, если горизонтальный луч из неё пересекает контур
нечётное число раз. Условие `(y1 > y) != (y2 > y)` отбирает только те рёбра, которые лежат
по разные стороны от горизонтали — то есть действительно пересекают её. Дальше для каждого
такого ребра считается x-координата пересечения, и если она правее точки, пересечение
засчитывается.

Матрица `(N, M)` — это все пары «точка × ребро» сразу, без циклов на Python.

### 2.6 Батчи: почему по 800 точек

Векторизация решает задачу по скорости, но создаёт новую: массив `(N, M)` из 47 658 × 8 307
это 396 млн чисел по 8 байт — около 3 ГБ на одну такую матрицу, и её ещё несколько. Поэтому
обработка идёт порциями:

```python
def inside(pts, batch=800):
    out = np.zeros(len(pts), dtype=bool)
    for i in range(0, len(pts), batch):
        chunk = pts[i:i + batch]                    # 800 × 8 307 ≈ 6,6 млн чисел ≈ 53 МБ
        m = ray_inside(outer, chunk)
        for h in holes:
            m &= ~ray_inside(h, chunk)              # вырезаем внутренние дырки
        out[i:i + batch] = m
    return out
```

Размер порции выбран как компромисс: 53 МБ на массив помещается в память с запасом, а накладные
расходы на 60 итераций незаметны.

### 2.7 Потоковая обработка файла на 775 МБ

Выгрузка OSM не читается в память целиком. osmium подаёт объекты по одному в обработчик:

```python
class Collector(osmium.SimpleHandler):
    def node(self, n): ...
    def way(self, w): ...

h = Collector()
h.apply_file(PBF, locations=True)   # locations=True — osmium сам строит индекс координат
```

`locations=True` означает, что для линий osmium подгружает координаты их узлов — именно поэтому
разбор занимает около получаса и требует памяти: строится индекс. Наружу из обработчика
выносятся только отобранные объекты (2 432 из 112 млн узлов), а не весь файл.

## 3. Разбор по скриптам

### 3.1 `download_rosstat.py` — загрузка сборника (42 строки)

**Назначение.** Скачать архив и PDF сборника «Регионы России — 2025» с сайта Росстата.

| | |
|---|---|
| Вход | сайт `rosstat.gov.ru` |
| Выход | `data/rosstat/Region_Pokaz_2025.rar`, `.pdf` |

**Как работает.** Список файлов задан таблицей «имя → путь на сайте», дальше цикл скачивания
порциями по 1 МБ с прогрессом:

```python
FILES = [("Region_Pokaz_2025.rar", "/storage/mediabank/Region_Pokaz_2025.rar"), ...]

while True:
    chunk = r.read(1 << 20)        # 1 МБ = 2**20
    if not chunk:
        break
    f.write(chunk)
```

Читать ответ целиком нельзя: PDF сборника — десятки мегабайт, и `r.read()` без аргумента
занял бы память целиком. Порционная запись даёт ещё и прогресс.

**Тонкости.** Заголовок `User-Agent` подставлен от браузера — сайты госструктур часто отдают 403
на «неизвестного клиента». Проверка сертификата отключена (`ssl._create_unverified_context()`) —
это компромисс, а не хорошая практика: на машине автора стандартная проверка цепочки
сертификатов Росстата не проходила.

> **Замечание по коду.** На строке 24 остался мёртвый фрагмент:
> `url = BASE + urllib.parse.quote(path) if False else BASE + path` — ветка с `if False`
> никогда не выполняется, это след эксперимента с кодированием URL. Строку стоит заменить на
> `url = BASE + path`.

### 3.2 `get_region_boundary.py` — граница области (36 строк)

**Назначение.** Получить полигон административной границы Саратовской области.

| | |
|---|---|
| Вход | Nominatim (OpenStreetMap), запрос «Саратовская область, Россия» |
| Выход | `data/osm/region_boundary.geojson` (8 307 точек внешнего контура) |

**Как работает.** Один HTTP-запрос с параметром `polygon_geojson=1`, ответ сохраняется как
GeoJSON. Вспомогательная функция `rings()` умеет разбирать и `Polygon`, и `MultiPolygon`.

**Тонкости.** Nominatim требует осмысленный `User-Agent` — подставлен
`region-econ-research/1.0 (student research)`. Без него сервис отвечает 403.

**Зачем граница вообще нужна.** Это ключ к пространственной точности: прямоугольник вокруг
области (bbox) захватывает пять соседних регионов и часть Казахстана, поэтому фильтровать
объекты нужно по реальному контуру.

### 3.3 `download_osm_pbf.py` — выгрузка OSM (34 строки)

| | |
|---|---|
| Вход | Geofabrik, `volga-fed-district-latest.osm.pbf` |
| Выход | `data/osm/*.osm.pbf` (775 МБ) |

**Как работает.** То же порционное скачивание, но порция 4 МБ и прогресс каждые 100 МБ.
Проверка «уже скачано» сравнивает размер с 0,7 ГБ.

**Почему Geofabrik, а не Overpass API.** Изначально объекты собирались через Overpass
(запрос по области с тегами). Сервис сначала начал фильтровать запросы по `User-Agent`, затем
не выдержал запрос по целой области (таймаут 912 с) и в итоге заблокировал IP клиента.
Выгрузка PBF снимает зависимость от чужого API: файл скачивается один раз и разбирается локально,
сколько угодно раз и без лимитов.

Цена решения — объём: 775 МБ на диске и около получаса на разбор вместо одного HTTP-запроса.
Плюс побочный выигрыш: локальный разбор даёт **все** объекты региона, а не только те, что
попали в ответ API.

### 3.4 `parse_vacancies_trudvsem.py` — вакансии (117 строк)

| | |
|---|---|
| Вход | API `opendata.trudvsem.ru`, регион `6400000000000` |
| Выход | `data/labor/vacancies.csv` (4 183 × 15), `vacancies_raw.json` |

**Главная проблема и её решение.** API отдаёт не больше 200 записей на запрос:
`offset + limit ≤ 200`. При 7 939 активных вакансиях постраничный обход невозможен — на второй
странице сервис отвечает ошибкой. Решение: разбить выборку не по страницам, а **по ключевым
словам профессий**:

```python
KEYWORDS = """водитель продавец менеджер инженер учитель ...""".split()
KEYWORDS = list(dict.fromkeys(KEYWORDS))     # убираем повторы, сохраняя порядок

def collect_kw(kw):
    got = {}
    for offset in (0, 100):                  # максимум 200 записей на слово
        d = fetch(kw, offset)
        if not d:
            break
        ...
        if len(vacs) < 100:                  # страница неполная — дальше записей нет
            break
    return kw, got
```

Приём `dict.fromkeys(...)` — идиома «уникализировать список с сохранением порядка»: словарь
в Python помнит порядок вставки, а повторы ключей отбрасываются.

**Парсинг ответа.** Структура ответа вложенная, поэтому доступ идёт через цепочки `or {}`:

```python
addr = ((v.get("addresses") or {}).get("address") or [{}])
a0 = addr[0] if addr else {}
```

Такой шаблон безопасен: если `addresses` отсутствует или равно `None`, выражение не падает,
а даёт пустой словарь. То же для `company` и `requirement`.

**Запись CSV.** Разделитель — точка с запятой (в русских названиях часто есть запятые),
кодировка `utf-8-sig`, чтобы Excel правильно открыл файл, а кавычки внутри значений заменяются
на апострофы:

```python
f.write(";".join('"%s"' % str(row[c]).replace('"', "'") for c in cols) + "\n")
```

**Тонкости.** Первая адресная запись берётся как основная (`addr[0]`) — у вакансии может быть
несколько адресов. Поле `city` заполняется значением `city`, а если его нет — обрезанной строкой
`location`. Итоговая строка отчёта «из 7939» зашита текстом — это константа, а не вычисленное
значение.

### 3.5 `rosstat_docx_to_text.py` — docx в текст (48 строк)

| | |
|---|---|
| Вход | 22 файла `R_*.docx` (распакованные разделы сборника) |
| Выход | `data/rosstat/Region_Pokaz_2025/txt/R_*.txt` (823 таблицы) |

**Неочевидная часть — порядок блоков.** У документа Word абзацы и таблицы лежат в одном потоке,
но `python-docx` отдаёт их раздельными списками (`doc.paragraphs`, `doc.tables`), и порядок
теряется. Поэтому тело документа обходится на уровне XML:

```python
def iter_block_items(parent):
    from docx.oxml.ns import qn
    for child in parent.element.body.iterchildren():
        if child.tag == qn("w:p"):
            yield Paragraph(child, parent)
        elif child.tag == qn("w:tbl"):
            yield Table(child, parent)
```

`qn("w:p")` — это «квалифицированное имя» тега: `w:p` разворачивается в полный адрес
`{namespace}paragraph`. Так мы видим абзацы и таблицы в том порядке, в котором они в документе.

**Формат вывода** — собственный текстовый формат с маркерами:

```
--- ТАБЛИЦА 3 ---
Показатель | 2010 | 2015 | 2020
Саратовская область | 2519,3 | 2493,0 | 2457,6
--- КОНЕЦ ТАБЛИЦЫ 3 ---
```

Ячейки разделены `|`, неразрывные пробелы (`\xa0`) заменены обычными, переводы строк внутри
ячейки — пробелами. Такой дамп легко читать и парсить регулярками, не поднимая Word.

### 3.6 `rosstat_extract_region.py` — выборка региона (74 строки)

| | |
|---|---|
| Вход | текстовые дампы `txt/R_*.txt` |
| Выход | `saratov_tables.json`, `saratov_tables.txt` |

**Как работает.** Файл разбирается построчно; таблицы выделяются по маркерам:

```python
if ln.startswith("--- ТАБЛИЦА"):     cur = []
elif ln.startswith("--- КОНЕЦ ТАБЛИЦЫ"): tables.append((title, cur)); cur = None
elif cur is None:                    pending.append(ln)   # текст до таблицы
else:                                cur.append(ln)       # строки таблицы
```

Заголовок таблицы берётся как последняя непустая строка **перед** таблицей — для этого и нужен
буфер `pending`. В сборнике название таблицы стоит не в подписи «Таблица 1.1», а строкой выше
самой сетки, поэтому такой поиск назад оказывается точнее, чем поиск по номеру.

Для каждой таблицы сохраняются: имя файла, название раздела, заголовок таблицы, две первые
строки (шапка) и все строки, где встретился регион.

> **Расхождение, найденное при проверке.** Отбор строк идёт только по **первой** ячейке:
>
> ```python
> hit = [r for r in rows if r.split("|")[0].strip().startswith(SAR)]
> ```
>
> При этом документация проекта утверждает, что регион ищется «по любой ячейке строки».
> Проверка на реальных дампах даёт: **397 таблиц** при поиске по первой ячейке против
> **476 таблиц** при поиске по любой ячейке. То есть текущий скрипт пропускает **79 таблиц** —
> это «продолжения» больших таблиц (`Продолжение табл. 1.1`, `Продолжение табл. 3.5`, …), где
> название региона по формату вёрстки оказалось в одном из средних столбцов.
>
> Лечится одной строкой: `if SAR in r`. Подробнее — в разделе 5.

### 3.7 `parse_osm_objects.py` — объекты из OSM (141 строка)

| | |
|---|---|
| Вход | PBF 775 МБ + полигон границы |
| Выход | `data/osm/objects.csv` (2 432 × 14), `objects.json` |

Самый содержательный скрипт проекта. Три части: отбор по тегам, фильтр по границе, запись.

**Отбор по тегам** — функция `classify()` возвращает список категорий объекта. Один объект может
попасть в несколько категорий:

```python
def classify(t):
    out = []
    if t.get("amenity") == "bank":     out.append("bank")
    if t.get("amenity") == "atm":      out.append("atm")
    if t.get("industrial"):            out.append("industry")
    if t.get("shop") in ("supermarket", "convenience", "general"): out.append("shop")
    if t.get("shop") in ("beauty", "hairdresser", "massage") or t.get("leisure") == "tanning_salon":
        out.append("service")
    return out
```

Теги взяты из образца (чужой ВКР по Белгородской области) — это осознанное решение, чтобы
регионы сравнивались на одной методике. Обратите внимание: `industrial` проверяется на любое
значение, а `shop` — по списку; так сделано потому, что видов производств в OSM десятки, а
интересующих форматов торговли всего три.

**Узлы и линии.** Объекты в OSM бывают точками (`node`) и полигонами (`way`, например, здание
магазина или заводская площадка). Для линий берётся центр масс координат:

```python
pts = [(nr.location.lon, nr.location.lat) for nr in w.nodes if nr.location.valid()]
lon = sum(p[0] for p in pts) / len(pts)
lat = sum(p[1] for p in pts) / len(pts)
```

Это не геометрический центроид полигона, а среднее по вершинам — для размещения объекта этого
достаточно, а для сложных контуров разница несущественна.

**Фильтр по границе** — тот самый векторный лучевой метод из п. 2.5, применяется одним вызовом
ко всем кандидатам сразу:

```python
pts = np.array([[r["lon"], r["lat"]] for r in h.raw], dtype=np.float64)
mask = inside(pts)
rows = [r for r, keep in zip(h.raw, mask) if keep]
```

**Тонкости.** Счётчики обработанных узлов печатаются каждые 5 млн — по ним видно, что процесс
жив. `locations=True` в `apply_file` обязателен, иначе у линий не будет координат. Объекты без
валидных координат (`loc.valid()`) отбрасываются — это узлы, выходящие за пределы выгрузки.

### 3.8 `assign_cities.py` — привязка к городам (84 строки)

| | |
|---|---|
| Вход | `objects.csv` + кэш координат городов |
| Выход | `objects_by_city.csv` (+ колонка `settlement`) |

**Зачем.** В OSM поле `addr:city` заполнено редко, поэтому город определяется геометрически —
по ближайшему населённому пункту из списка 27 городов области.

**Как считается расстояние.** Не формула гаверсинуса, а более дешёвая равноугольная
аппроксимация: градус широты ≈ 111 км, градус долготы — 111 км, умноженные на косинус широты:

```python
def dist2(lat, lon, lat2, lon2):
    dlat = (lat - lat2) * 111.0
    dlon = (lon - lon2) * 111.0 * math.cos(math.radians((lat + lat2) / 2))
    return dlat * dlat + dlon * dlon
```

Функция возвращает **квадрат** расстояния — сравнивать квадраты дешевле, чем извлекать корень
для каждого из 27 кандидатов. Корень берётся один раз, для лучшего варианта. На широте
Саратова (52°) погрешность аппроксимации — доли процента, что для выбора ближайшего города
несущественно.

**Порог 30 км.** Если ближайший город дальше 30 км, объект относится в группу «прочие
населённые пункты»: иначе объект из глухого района приписался бы городу, до которого десятки
километров.

**Приоритет источника города.** Если в OSM всё-таки указан `addr:city`, он важнее расчётного:

```python
when = r["city"].strip() if r["city"].strip() else best
```

Логика: данные, указанные человеком, точнее вычисления по ближайшему городу.

### 3.9 `aggregate.py` — сводные таблицы (142 строки)

| | |
|---|---|
| Вход | `objects.csv`, `objects_by_city.csv`, `vacancies.csv` |
| Выход | `analiz/вакансии_топ_профессий.csv`, `analiz/вакансии_по_сферам.csv`, `analiz/объекты_по_городам.csv` |

**Как работает.** Три независимые функции: `money()` (банки и банкоматы), `labor()` (вакансии),
`goods()` (магазины, услуги, производства). Каждая проверяет наличие входного файла и печатает
таблицу в консоль, а итоги пишет в CSV.

**Разбор чисел** — вся числовая грязь собирается в одну функцию:

```python
def num(x):
    try:
        v = float(str(x).replace(",", ".").replace(" ", ""))
        return v if v > 0 else None
    except Exception:
        return None
```

Она снимает три типовые проблемы: запятая как десятичный разделитель, пробелы-разделители
разрядов, пустые значения. Ноль и отрицательные трактуются как «значения нет» — в вакансиях
это означает «зарплата не указана».

**Расчёт зарплатной статистики** — важная методическая деталь:

```python
sal = [num(r["salary_min"]) or num(r["salary_max"]) for r in rows]
```

Берётся **нижняя** граница вилки («от»), а верхняя используется только если нижней нет. Это
консервативная оценка: если вакансия предлагает «от 40 000 до 90 000», в расчёт идёт 40 000.
Медиана считается через `statistics.median`, квартили — через `statistics.quantiles`.

**Адаптация к схеме файла.** `goods()` работает и с привязанным, и с непривязанным файлом:

```python
key = "settlement" if "settlement" in (rows[0] if rows else {}) else "city"
```

Колонка группировки выбирается по факту наличия — скрипт не падает, если
`assign_cities.py` ещё не запускался.

**Словарь синонимов для печати** — технические категории OSM переводятся в человеческие:

```python
names = {"industry": "производства", "shop": "магазины", "service": "услуги"}
```

**Тонкости.** `Counter.most_common()` даёт готовую сортировку по убыванию — большая часть
аналитики в проекте построена на `Counter` и `defaultdict(Counter)`.

### 3.10 `make_presentation.py` — сборка презентации (~500 строк)

| | |
|---|---|
| Вход | шаблон СПбГУ + сводные данные |
| Выход | `Саратовская_область_презентация_СПбГУ.pptx` (19 слайдов) |

**Как работает.** Открывает официальный шаблон кафедры, удаляет из него демонстрационные слайды
и строит свои на его макетах:

```python
prs = Presentation(TEMPLATE)
xml_slides = prs.slides._sldIdLst
for sld in list(xml_slides):
    prs.part.drop_rel(sld.rId)      # сначала разрываем связь с частью
    xml_slides.remove(sld)          # потом удаляем сам слайд
```

Порядок обязателен: если просто удалить слайд из XML-списка, его часть останется в пакете
файла и раздуёт его. `drop_rel` разрывает связь, затем элемент удаляется целиком.

**Свой слой примитивов.** Вместо работы с плейсхолдерами напрямую написаны функции-обёртки
`box()`, `card()`, `bullets()`, `table()`, `kpi_row()`, `chart()`, `source()`, `notes()`.
Каждая принимает координаты в дюймах и сама задаёт шрифт, размер и цвет — это позволяет держать
единый стиль и описывать слайд несколькими вызовами.

**Оформление таблиц** задаётся вручную, потому что своего стиля у `python-pptx` нет:

```python
cell.fill.solid()
cell.fill.fore_color.rgb = RED_DARK if r == 0 else (LIGHT if r % 2 else WHITE)
```

Шапка — фирменный тёмно-красный, строки — «зебра» для читаемости.

**Диаграммы** строятся на нативных диаграммах PowerPoint (не картинками), поэтому остаются
редактируемыми в PowerPoint. Цвета серий задаются по точкам:

```python
for i, point in enumerate(plot.series[0].points):
    point.format.fill.solid()
    point.format.fill.fore_color.rgb = colors[i % len(colors)]
```

**Заметки докладчика** пишутся в `slide.notes_slide` — в режиме докладчика текст виден только
выступающему.

**Тонкость.** Весь текст слайдов (включая числа) зашит в код — скрипт **не читает** `analiz/`
и `saratov_tables.json`. Об этом ниже.

## 4. Что автоматизировано, а что введено руками

Это важно понимать до защиты: не все числа рождаются в скриптах.

| Блок | Полностью автоматически | Введено вручную |
|---|---|---|
| Вакансии | всё: сбор → CSV → топы профессий, сфер, зарплатные квартили, концентрация работодателей | — |
| Объекты OSM | всё: PBF → фильтр по границе → привязка к городам → сводные таблицы | — |
| Статистика Росстата | распаковка 22 разделов, перевод в текст, отбор 397 таблиц со строкой региона | **числа из таблиц в аналитику и слайды переносятся вручную** |
| Презентация | сборка на шаблоне, диаграммы, заметки | весь текст и числа зашиты в код |

Конкретно: файл `saratov_tables.json` создаётся скриптом, но производные показатели по
финансовому блоку (доля Сбербанка, вклады на душу, кратный рост) считались отдельным скриптом,
где **ряды вписаны в код руками**:

```python
dep_total = {2011: 97314, 2016: 209802, 2021: 293944, 2023: 404133, 2024: 453707, 2025: 585130}
sber_ind  = {2011: 50930, 2016: 96870, 2021: 146814, 2023: 180611, 2024: 215819, 2025: 266542}
```

Риск понятен: при опечатке в одной цифре ошибка не будет поймана — контрольной сверки с
`saratov_tables.json` нет. Для защиты это уязвимое место: вопрос «покажите, как из сборника
получилось 585 130» упирается в то, что значение набрано руками из таблицы 20.10.

**Чего ещё нет в репозитории.** Скрипты производных показателей (финансовый, трудовой, товарный
блоки) остались в рабочей папке автора и в проект не попали — в `scripts/` есть только
`aggregate.py`, который считает вакансии и объекты OSM. То есть числа вида «372 объекта в
Саратове», «51,8% вкладов в Сбербанке», «медиана 27 093 ₽ в образовании» воспроизводятся только
на машине автора.

### 4.1 Проверка: какие числа действительно получены скриптом

Чтобы не оценивать на глаз, 25 ключевых показателей презентации были автоматически сверены с
содержимым `saratov_tables.json` — тем, что реально извлекла программа. Результат: **18 значений
найдены в машинной выборке, 7 — нет.**

| Ненайденный показатель | Значение | Где лежит в исходнике |
|---|---|---|
| Вклады всего, 2025 | 585 130 млн ₽ | `R_20.txt`, строка оканчивается на «Саратовская область» |
| Вклады населения, 2025 | 514 711 млн ₽ | там же |
| Вклады юрлиц, 2025 | 70 419 млн ₽ | там же |
| Обрабатывающие производства | 799 млрд ₽ | `R_01.txt`, строка оканчивается на «Саратовская область» |
| Продукция АПК | 282,1 млрд ₽ | там же |
| Оборот розницы | 648,5 млрд ₽ | там же |

Исходные строки выглядят так:


Практический вывод: после исправления фильтра (397 → 476 таблиц) те же 25 значений проверяются
машинно, а не сверкой на глаз.

## 5. Найденные расхождения и что с ними делать

Перечислено по убыванию важности.

**1. Пропущено 79 таблиц сборника (важно).** `rosstat_extract_region.py` ищет регион только
в первой ячейке строки, документация заявляет поиск по любой. Замер: 397 против 476 таблиц;
пропущены «продолжения» таблиц 1.1, 3.5, 3.6, 3.7, 4.11 и других. Однострочное исправление
(`if SAR in r`) + повторный запуск. Потребует обновить число «397 таблиц» в презентации,
техническом описании и разборах.

**2. Производные показатели считаются скриптами вне репозитория.** Три скрипта
(`fin_metrics.py`, `labor_metrics.py`, `goods_metrics.py`) лежат в рабочей папке и не
опубликованы. Их стоит перенести в `scripts/` как `metrics_finance.py`, `metrics_labor.py`,
`metrics_goods.py` — тогда каждое число презентации будет воспроизводиться одной командой.

**3. Ряды Росстата введены руками.** Показатели финансового блока стоит читать из
`saratov_tables.json` по номеру таблицы, а не хранить в словарях кода. Это снимет риск опечатки
и даст возможность честно сказать «числа берутся из сборника программно».

**4. Мёртвый код в `download_rosstat.py`** (строка 24, `if False`) — убрать.

**5. Неиспользуемая константа `TOOLS`** в 10 скриптах из 11: путь к локальным зависимостям
нужен только `parse_osm_objects.py` (numpy, osmium). В остальных строка безвредна, но
вводит в заблуждение — можно удалить.

**6. Отключённая проверка TLS** (`ssl._create_unverified_context()`) в четырёх скриптах —
технический долг: правильнее починить цепочку сертификатов, чем отключать проверку.

**7. Регион зашит в код.** Код региона `6400000000000` и строка «Саратовская область» заданы
константами в четырёх местах. Для второго региона проект придётся править, хотя структура
позволяет вынести это в параметр командной строки.

**8. Скрипт презентации не читает сводные таблицы.** Числа на слайдах не связаны с `analiz/`:
если данные пересчитать, слайды не изменятся. Полноценное решение — читать значения из
`saratov_tables.json` и CSV, но для разового доклада это оправданный компромисс.
